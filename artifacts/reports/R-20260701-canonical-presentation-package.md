# Report: BriefForge Canonical Presentation Package

Date: 2026-07-01
Type: constitutional-investigation
Status: Final
Owner: BriefForge
Scope: smallest canonical Presentation Package only

## 1. Scope

This report answers one constitutional question:

> What is the smallest canonical Presentation Package that BriefForge exists to own?

This report does not perform a broad architectural review.

This report does not authorize implementation.

This report does not define a serialization format, schema, API, runtime, project structure, product workflow, or delivery technology.

The question is purely constitutional: identify the irreducible object whose ownership justifies BriefForge as an independent project.

## 2. Executive conclusion

The smallest canonical Presentation Package is:

> A bounded semantic presentation object that declares a presentation purpose, contains an ordered set of presentation statements, attaches each statement to upstream-owned references where required, preserves all presentation obligations attached to those references, and states only target-independent presentation intent.

The package is canonical because it is the authoritative BriefForge-owned object.

The package is not canonical because of any delivery target or external technology.

The package owns presentation meaning only.

It references economic meaning and analytical meaning owned elsewhere.

It excludes delivery meaning.

Recommendation:

> Canonical Presentation Package established.

However, Constitution Freeze should still wait until this report is incorporated into the constitution and reconciled with the existing open-question list.

## 3. Definition of the canonical Presentation Package

A canonical Presentation Package is the smallest self-contained semantic object that can answer:

1. What is being presented?
2. Why is it being presented?
3. In what order should the presented material be encountered?
4. Which upstream-owned material supports or supplies each presentation statement?
5. Which obligations must remain attached when the material is presented?
6. What presentation-local constraints must be true for the package to be valid?

The package is not the upstream evidence.

The package is not the upstream conclusion.

The package is not the final delivered artifact.

The package is the constitutional bridge between upstream-owned meaning and future presentation consumption.

## 4. Constitutional justification

BriefForge is justified only if it owns a distinct artifact that no upstream project, scaffold project, or future user-facing system should own.

The canonical Presentation Package satisfies this condition because:

1. It is not an economic observation.
2. It is not a source-specific interpretation.
3. It is not a canonical data product.
4. It is not an analytical conclusion.
5. It is not a governance scaffold.
6. It is not a user navigation object.
7. It is not a delivery artifact.

Its distinct responsibility is:

> preserve presentation meaning while preserving upstream ownership.

Without this object, presentation meaning would either disappear into ad hoc documents or be absorbed into upstream projects that should not own presentation composition.

## 5. Required elements

The smallest valid Presentation Package requires exactly five categories.

### 5.1 Package identity

The package must identify itself as a bounded presentation object.

Required identity answers:

- what the package is;
- what presentation purpose it serves;
- what scope it claims;
- what scope it explicitly does not claim.

This is presentation identity, not ecosystem routing, publication status, search classification, or user prioritization.

Why required:

Without identity, there is no bounded object to validate.

### 5.2 Presentation thesis or organizing question

The package must state the organizing reason for the presentation.

This can be a neutral question, topic, comparison, analytical frame, or stated upstream thesis.

It must not create unsupported economic or analytical meaning.

Examples:

- “Present the economic profile of Denmark.”
- “Compare Denmark and Sweden on selected upstream-owned indicators.”
- “Present the upstream-owned investment thesis and its supporting/cautionary material.”

Why required:

Without an organizing reason, ordering is arbitrary and the package becomes a bundle of references rather than a presentation.

### 5.3 Ordered presentation statements

The package must contain one or more presentation statements.

A presentation statement is the smallest unit of presentation meaning.

It says:

- what should be encountered;
- how it relates to the organizing purpose;
- whether it is introductory, evidential, comparative, cautionary, contextual, or concluding at the presentation level.

A presentation statement must not be confused with an upstream economic claim or analytical conclusion.

It may contain upstream-authored content by reference or approved excerpt.

It may contain presentation-local connective meaning such as “this comes before that,” “this qualifies that,” or “this evidence supports the displayed upstream finding.”

Why required:

Without ordered presentation statements, BriefForge has no composition responsibility.

### 5.4 Upstream-owned references

A presentation statement must reference upstream-owned material whenever it depends on external economic evidence, analytical findings, definitions, caveats, confidence, freshness, or provenance.

The reference establishes:

- who owns the upstream meaning;
- what upstream material is being used;
- what part is relevant;
- what obligations travel with it.

The reference does not transfer ownership.

Why required:

Without upstream-owned references, BriefForge either owns meaning it should not own or produces unverifiable presentation text.

### 5.5 Presentation obligations

The package must preserve presentation obligations attached to upstream material.

The irreducible obligation categories are:

1. Ownership visibility: the upstream owner must remain identifiable.
2. Evidence visibility: required evidence/provenance must not be suppressed.
3. Caveat visibility: required caveats and scope limits must remain attached.
4. Confidence visibility: supplied confidence or uncertainty must not be hidden.
5. Freshness visibility: supplied date, vintage, review state, or staleness must not be hidden when material to interpretation.
6. Non-transformation: the presentation must not change upstream meaning.
7. Non-detachment: a claim, figure, finding, or excerpt must not be separated from required obligations.

Why required:

Without obligations, presentation can make upstream material look stronger, cleaner, newer, broader, or more certain than it is.

## 6. Optional elements

The following may appear but are not required for every package.

### 6.1 Presentation audience

A package may state an intended audience or use context.

This is optional because some packages are general-purpose.

It must not become personalization or prioritization.

### 6.2 Presentation emphasis

A package may state that some presentation statements are more central than others.

This is optional because simple packages may rely on order alone.

Emphasis is presentation meaning only; it must not imply upstream truth strength unless the upstream owner supplies that strength.

### 6.3 Alternative paths through the same statements

A package may state target-independent alternative encounter paths, such as “overview first” or “evidence detail after summary.”

This is optional.

It must not define a delivery mechanism.

### 6.4 Approved excerpts

A package may include bounded excerpts from upstream-owned material when reference alone would be insufficient for presentation review.

An excerpt remains upstream-owned.

The package owns only the decision to include the excerpt in the presentation object.

### 6.5 Presentation-local notes

A package may include notes that clarify presentation structure, such as “comparison is ordered by geography” or “cautionary material follows supporting material.”

Such notes must not introduce new economic or analytical claims.

## 7. Semantics, intent, references, and exclusions

### 7.1 Parts that describe semantics

The semantic parts are:

- package identity;
- organizing question or purpose;
- ordered presentation statements;
- relationship among statements;
- obligation attachment;
- presentation-local validity conditions.

These are BriefForge-owned because they define presentation meaning.

### 7.2 Parts that describe presentation intent

Presentation intent is target-independent guidance about how meaning should be encountered.

Examples:

- present a profile before comparison;
- keep caveats adjacent to the relevant statement;
- show supporting and cautionary material as distinct presentation roles;
- preserve a stated contrast between two upstream-owned facts or findings;
- allow optional detail expansion conceptually, without specifying how.

Presentation intent belongs to BriefForge only when it remains independent of delivery mechanism.

### 7.3 Parts that merely reference upstream information

The package may reference:

- economic observations;
- data evidence;
- analytical findings;
- company facts;
- definitions;
- caveats;
- confidence statements;
- freshness or review status;
- source provenance.

These references do not become BriefForge-owned meaning.

### 7.4 Parts that must never appear

The package must not contain:

- data acquisition logic;
- canonicalization logic;
- source-specific economic interpretation;
- new economic conclusions not supplied by an upstream owner;
- new analytical judgments not supplied by an upstream owner;
- investment recommendations unless upstream-owned and explicitly referenced;
- delivery-specific instructions;
- user-routing or user-prioritization logic;
- generic component libraries;
- report-specific taxonomy pretending to be constitutional architecture.

## 8. Ownership boundaries

### 8.1 Economic meaning

Economic meaning answers:

- what the data is;
- what units, frequency, geography, source semantics, transformations, and canonical meaning apply;
- what a measurement means.

BriefForge does not own economic meaning.

BriefForge references economic meaning.

Reason:

If BriefForge changes economic meaning, it becomes an upstream data or analysis project rather than a presentation project.

### 8.2 Analytical meaning

Analytical meaning answers:

- what conclusion is justified;
- what confidence applies;
- what caveats constrain the conclusion;
- what inference has been made.

BriefForge does not own analytical meaning.

BriefForge references analytical meaning and preserves its obligations.

Reason:

If BriefForge creates analytical meaning, presentation becomes analysis.

### 8.3 Presentation meaning

Presentation meaning answers:

- what upstream-owned material is selected into this presentation object;
- why it is included for this presentation purpose;
- in what order it is encountered;
- how statements relate as presentation statements;
- which obligations must remain attached;
- what presentation-local validity constraints apply.

BriefForge owns presentation meaning.

Reason:

This is the irreducible responsibility that cannot be cleanly absorbed elsewhere.

### 8.4 Delivery meaning

Delivery meaning answers how the package becomes visible or operational in a specific medium, surface, or user environment.

BriefForge does not own delivery meaning at the constitutional package level.

Reason:

If the package encodes delivery meaning, it stops being independent of future technologies.

## 9. Relationship between Presentation Package and Presentation Contract

The Presentation Package and Presentation Contract are separate but inseparable constitutional concepts.

They are not identical.

They are not peers of equal independence.

The Presentation Contract derives from the Presentation Package.

Precise relationship:

- The Presentation Package is the constitutional object BriefForge owns.
- The Presentation Contract is the set of rules that determines whether something qualifies as a valid Presentation Package.
- Composition Semantics and Presentation Validation Obligations are parts of the contract because they define package validity.

Therefore:

```text
Presentation Package = owned canonical object
Presentation Contract = constitutional validity boundary for that object
```

Why this matters:

If the contract comes first without a package, BriefForge risks becoming an abstract rules project.

If the package exists without a contract, BriefForge cannot validate its own canonical object.

The package is primary. The contract is derived to protect it.

## 10. Conceptual examples

These examples are abstract. They are not report archetypes, schemas, or implementation formats.

### 10.1 Country Profile

A Country Profile package can be represented as:

- identity: bounded presentation of one country;
- organizing purpose: present selected upstream-owned facts and findings about the country;
- ordered statements:
  - identify the country and presentation scope;
  - present upstream-owned economic indicators;
  - present upstream-owned caveats about data coverage or freshness;
  - present upstream-owned analytical findings if supplied;
  - present limitations of the profile;
- references: country identity, indicators, observations, findings, caveats;
- obligations: show sources, date/vintage, caveats, confidence where supplied.

No country-specific constitutional concept is required.

Result: abstraction holds.

### 10.2 Country Comparison

A Country Comparison package can be represented as:

- identity: bounded presentation comparing two or more countries;
- organizing purpose: present selected similarities and differences using upstream-owned material;
- ordered statements:
  - define comparison scope;
  - present comparable upstream-owned material for each country;
  - identify presentation-level contrast points;
  - attach caveats where comparability is limited;
  - preserve upstream-owned analytical conclusions if present;
- references: country-specific upstream material and any comparability caveats;
- obligations: show source differences, coverage differences, confidence/freshness, and non-comparability caveats.

The package does not calculate comparability or transform indicators. It only presents referenced comparability constraints.

Result: abstraction holds.

### 10.3 Investment Thesis

An Investment Thesis package can be represented as:

- identity: bounded presentation of an upstream-owned thesis;
- organizing purpose: present the thesis, support, risks, caveats, and evidence without changing the thesis;
- ordered statements:
  - state the upstream-owned thesis;
  - present supporting upstream-owned evidence;
  - present opposing or cautionary upstream-owned material;
  - present confidence and scope limits supplied by the owner;
  - present unresolved questions;
- references: thesis artifact, evidence artifacts, caveats, confidence statement;
- obligations: do not strengthen conviction, suppress risks, or detach thesis from caveats.

The package does not create the thesis.

Result: abstraction holds.

### 10.4 Company Analysis

A Company Analysis package can be represented as:

- identity: bounded presentation concerning a company;
- organizing purpose: present upstream-owned facts, findings, and caveats about the company;
- ordered statements:
  - identify company and scope;
  - present upstream-owned company facts;
  - present upstream-owned economic or financial context;
  - present upstream-owned analytical findings if supplied;
  - present limitations and caveats;
- references: company facts, observations, findings, caveats, confidence/freshness;
- obligations: preserve source ownership, review status, caveats, and uncertainty.

The package does not perform company analysis.

Result: abstraction holds.

### 10.5 Indicator Explorer

An Indicator Explorer package can be represented only if “explorer” is interpreted constitutionally as a bounded presentation of upstream-owned indicator material and possible target-independent encounter paths.

It can contain:

- identity: bounded presentation of one or more indicators;
- organizing purpose: help encounter upstream-owned indicator facts, caveats, and context;
- ordered statements:
  - define indicator scope;
  - present upstream-owned indicator identity and caveats;
  - present selected upstream-owned observations or summaries;
  - present optional conceptual paths such as overview, detail, or caveats;
- references: indicator definitions, observations, metadata, caveats;
- obligations: preserve units, frequency, geography, source, freshness, caveats.

It must not contain:

- live query behavior;
- transformation behavior;
- exploration mechanics;
- user-state behavior;
- delivery-specific controls.

Result: abstraction holds only after stripping “Explorer” down to presentation meaning. If “Explorer” requires operational exploration behavior, it belongs outside the canonical package.

## 11. Falsification attempts and results

### Attempt 1: Remove package identity

Result: fails.

Without identity, there is no bounded object to validate.

Keep.

### Attempt 2: Remove organizing purpose

Result: fails.

Without an organizing purpose, the package becomes a bag of references. That eliminates presentation meaning.

Keep.

### Attempt 3: Remove ordered presentation statements

Result: fails.

Without ordered statements, BriefForge no longer owns composition semantics.

Keep.

### Attempt 4: Remove upstream-owned references

Result: fails.

Without references, the package either owns upstream meaning or becomes unverifiable.

Keep.

### Attempt 5: Remove presentation obligations

Result: fails.

Without obligations, presentation can hide caveats, freshness, confidence, or ownership. This eliminates BriefForge’s distinct validation role.

Keep.

### Attempt 6: Remove optional audience

Result: succeeds.

Audience is useful but not irreducible.

Keep optional only.

### Attempt 7: Remove optional emphasis

Result: succeeds.

Order and relationship are sufficient for the smallest package.

Keep optional only.

### Attempt 8: Remove approved excerpts

Result: succeeds for many packages, but not necessarily all.

References alone may be enough constitutionally. Excerpts remain optional and upstream-owned.

### Attempt 9: Assign package ownership to upstream data or analysis projects

Result: fails.

That would force upstream projects to own presentation composition and obligation-preserving cross-source arrangement.

Keep in BriefForge.

### Attempt 10: Assign package ownership to a future user-facing system

Result: fails.

That would mix presentation meaning with user routing, prioritization, or consumption behavior.

Keep in BriefForge.

### Attempt 11: Encode delivery decisions in the package

Result: rejected.

Delivery decisions are not necessary for the canonical package and would violate technology independence.

Exclude.

### Attempt 12: Encode report-specific structures

Result: rejected.

The examples all fit using identity, organizing purpose, ordered statements, references, and obligations. Report-specific concepts are unnecessary.

Exclude.

## 12. Relationship to prior blocking questions

### 12.1 Smallest valid presentation contract

Status after this report: substantially resolved.

The smallest contract is the validity rule for the five required package categories:

1. package identity;
2. organizing purpose;
3. ordered presentation statements;
4. upstream-owned references where dependency exists;
5. presentation obligations.

### 12.2 Reference-only versus bounded display snapshot

Status after this report: partly resolved.

The canonical package does not require snapshots as a universal element.

It requires upstream-owned references.

Bounded excerpts may appear only as optional upstream-owned presentation material when reference-only presentation is insufficient for review.

Therefore the constitutional default becomes reference-first, excerpt-optional, no local data ownership.

### 12.3 Exact presentation obligations

Status after this report: substantially resolved.

The irreducible obligations are ownership, evidence/provenance, caveat/scope, confidence/uncertainty, freshness/review state, non-transformation, and non-detachment.

### 12.4 Presentation-local validation boundary

Status after this report: substantially resolved.

Validation checks whether the package contains the required categories and preserves obligations without changing upstream meaning.

It does not validate upstream truth or analytical correctness.

### 12.5 Visual-slot versus visualization-specification versus renderer boundary

Status after this report: reframed and mostly removed from the package question.

The canonical package does not need a visual-slot concept.

If upstream-owned material includes a displayable item, the package may reference that material and preserve obligations. Any further delivery-specific meaning is outside the canonical package.

### 12.6 Target-independent interaction intent

Status after this report: narrowed.

Only target-independent encounter intent is allowed, and it is optional. It cannot define interaction mechanics.

### 12.7 Minimum self-description metadata

Status after this report: resolved at constitutional minimum.

Self-description is package identity plus organizing purpose plus scope and non-scope. Additional metadata is optional.

## 13. Remaining constitutional uncertainties

### 13.1 Whether approved excerpts are ever required

The report establishes references as required and excerpts as optional.

Remaining uncertainty:

- Is there any valid package class where reference-only presentation cannot be reviewed without an excerpt?

This is important but no longer blocks defining the canonical package.

### 13.2 Whether presentation emphasis should become required

The report keeps emphasis optional.

Remaining uncertainty:

- Would some future packages require explicit emphasis to avoid misleading ordering?

This is non-blocking because order and obligations already provide the minimum.

### 13.3 Whether package identity needs a stable naming convention

The report requires identity but does not specify naming conventions.

This is non-blocking because naming convention is not constitutional at this level.

### 13.4 Whether package validation can remain purely presentation-local in all cases

The report defines the boundary, but future pressure may arise when presentation-local contradiction appears to depend on upstream truth.

This is important but non-blocking if the constitution says BriefForge may flag unresolved upstream dependency conflicts without resolving them.

## 14. Final recommendation

Recommendation: Canonical Presentation Package established.

The package is stable enough to serve as BriefForge’s constitutional foundation.

It is not yet a full Constitution Freeze recommendation by itself. Freeze would require incorporating this definition into the constitution and ensuring remaining constitutional language no longer contradicts it.

Final constitutional object:

> The canonical Presentation Package is a bounded semantic presentation object consisting of package identity, organizing purpose, ordered presentation statements, upstream-owned references where required, and presentation obligations. It owns presentation meaning only; it references economic and analytical meaning; it excludes delivery meaning.
